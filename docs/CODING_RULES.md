# 编码规范

## 1. 总则

遵循[技术架构](ARCHITECTURE.md)和[数据库设计](DATABASE.md)，每次只做满足当前阶段要求的最小必要修改。

修改前阅读相关文件和调用关系，不引入未要求的依赖、抽象、服务或 P2 功能。

使用 4 空格缩进，变量使用 camelCase，函数名以动词开头；Payload 和数据库已有字段名保持既定命名，不做无意义转换。

代码注释优先使用中文，只解释代码本身无法表达的约束和原因。

## 2. TypeScript

- 使用 TypeScript 统一前后端类型，避免以 `any` 绕过业务模型和外部输入检查。
- 外部 GitHub 数据、LLM 输出和管理员输入在信任边界使用 Zod 验证。
- 资源类型、资源状态和任务状态使用统一类型，不在页面中散落魔法字符串。
- 保持原始内容、AI 建议和人工编辑字段的类型与存储边界清晰。
- 错误处理保留可诊断信息，不在日志中输出 Token 或其他敏感配置。

## 3. Next.js 与 React

- 前台优先使用 Server Components，在服务端通过 Payload Local API 获取公开资源。
- 仅在搜索交互、筛选抽屉等确需浏览器行为时使用客户端组件。
- 公开页面支持 SSR / ISR，使用 Metadata API 提供独立 SEO 信息。
- 公开查询只读取已发布资源，不在客户端暴露草稿、审核或后台数据。
- 不为前台调用重复实现一套 CRUD API，公开 API 仅按需开放。
- 共享 UI 遵循[设计系统](DESIGN_SYSTEM.md)，所有资源列表复用 SkillCard 和 SkillGrid。
- 使用普通分页，筛选和排序不得返回与条件不一致的数据。

## 4. Payload 与 PostgreSQL

- 数据实体使用 Payload Collections，实体关系使用 Relationships 和 Join 字段，不手工重复维护关联。
- 通过 Hooks 实现必要业务处理，通过 Custom Views 定制采集和审核工作台。
- `slug` 唯一，GitHub URL 规范化，同一仓库和子目录不能重复导入。
- 分类最多使用一级和二级，工具与平台由后台维护，不写死在前端。
- 原始内容和平台加工内容分开保存，历史版本不可因更新或下架被覆盖或删除。
- AI 结果进入待审核流程，只有管理员可以发布，任务模块不得自动发布。
- 后台、采集、编辑、审核和发布操作必须验证管理员权限。

## 5. 采集、任务与内容安全

- 使用 Payload Jobs Queue 异步执行采集、解析、AI 和同步任务，不在 HTTP 请求中同步执行采集。
- 任务记录运行状态、执行时间和失败信息，支持重试和幂等处理。
- 第一版只采集公开 GitHub 仓库和 Skills.sh 公开资源页面，不增加其他来源；处理访问频率、Token 配置和访问失败。
- 不执行 Skill 中的脚本、命令或仓库程序，不自动下载并运行任意程序。
- Frontmatter 异常进入异常审核，不直接丢弃资源。
- 外部 Markdown 必须安全渲染，过滤不安全 HTML 和链接，并实施外部资源下载与内容长度限制。
- 重新采集通过 Hash 判断变化，创建新版本且不覆盖管理员编辑的中文内容。
- AI 服务失败与原始采集任务分开记录，允许单独重试。

## 6. 测试规范

- 端到端测试放在 `tests/e2e`，视觉与响应式检查放在 `tests/visual`。
- 测试数据与生产数据隔离，真实采集验收使用公开 GitHub 资源，不依赖伪造成功结果。
- 核心端到端测试覆盖导入、解析、AI 独立失败与重试、人工审核、发布、搜索、详情和来源跳转。
- 数据测试覆盖重复导入、单仓库多 Skill、Hash 变化、历史版本和人工中文内容保护。
- 权限测试覆盖未授权后台访问、未发布内容公开查询和采集发布操作。
- 搜索测试覆盖名称、中英文名称、简介、标签、筛选、排序和普通分页。
- Markdown 测试覆盖所支持语法以及不安全 HTML 和链接。
- 响应式测试覆盖桌面、平板和移动端行为，具体断点按最终设计 Token 执行。
- 测试工具已于 2026-11-09 确定为 `vitest@5.1.0`、`@vitest/coverage-v8@5.1.0` 和 `@playwright/test@1.65.0`。
- 行、语句、函数和分支覆盖率目标均为 80%，从 Phase 2 业务代码开始执行；Phase 1 只运行真实工程冒烟测试。
- 当前基础 CI 执行 `npm run lint`、`npm run typecheck`、`npm test` 和 `npm run build`；Playwright 在具有真实业务页面与流程后纳入对应验收。

## 7. Git 规范

- 分支模型、提交信息格式和合并流程待确认，未确认前保持小而完整的修改。
- 每个提交只包含一个可说明的目的，不混入无关格式化或重构。
- 不提交环境密钥、Token、生产数据、本地依赖或构建产物。
- 原始 MVP 文档不得修改或删除，空目录使用 `.gitkeep` 保留。
- 提交前检查受影响文档链接、数据约束、状态流转和验收条件的一致性。
- 交付说明区分已实现、已验证和待确认事项，不将测试计划写成测试通过。

后续修改仍须按开发计划推进，不得提前实现后续阶段、P1、P2 或其他未确认业务。
